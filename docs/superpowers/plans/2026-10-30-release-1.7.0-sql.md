# Release 1.7.0: SQL Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read SQL files (`.sql`) honestly, so that strings, quoted identifiers and dollar-quoted bodies never read
as comments, and anything unterminated is exit 2. SQL is the sixteenth box in the README's languages grid.

**Architecture:**
- Add a self-contained character lexer, `agent_comment_lint/lexers/sql.py`, built on `LineBuilder` as
  `lexers/clike.py` is.
- Everything is in one family with two dialect modes. A file that shows a MySQL marker is read with MySQL rules;
  every other file is read with standard rules, which fit PostgreSQL, SQLite and T-SQL.
- `rules.py` has no `--` marker. The lexer places a `BlockLine` for each comment line itself, so C1 counts them
  without any change to `rules.py`.

**Tech Stack:** Python 3.9+ standard library and `unittest`.

**Spec:** `docs/superpowers/specs/2026-10-29-next-level-roadmap-design.md`, section 7 and section 9 items 7–9.

**Renumbering:** the plan `2026-10-29-release-1.5.0-languages.md` called Kotlin, Swift and C/C++ "1.7.0". They are
now 1.8.0.

## Review Focus

1. **Postgres function bodies (`$$ ... $$`)** hold plpgsql, whose `--` comments are real comments written by the
   agent. Expect them judged. Expect a body that does not lex to be skipped as content, never exit 2.
2. **mysqldump files** escape quotes as `\'` and open with `/*!40101 ... */` lines. Expect them to lex without
   exit 2. Expect the executable comments not to be read as prose.
3. **A multi-line string literal** (allowed in SQL) must never swallow later comments after it closes. One that never
   closes is exit 2.
4. **Postgres JSON operators** `#>`, `#>>` and `#-` are code, not comments.
5. **CRLF files** behave exactly as LF files.

### Task 1: SQL

**Files:**
- Create: `agent_comment_lint/lexers/sql.py`
- Modify: `agent_comment_lint/lexers/__init__.py`, `.pre-commit-hooks.yaml`, `tests/test_known_false_positives.py`,
  `docs/reference.md` ("Known false positives" rows only)
- Test: `tests/test_sql.py`

**Interfaces:**
- Consumes: `base.LineBuilder` (`emit`, `emit_span`, `emit_block_comment`, `newline` and `place`), `base.BlockLine`,
  `base.LexError`, `base.normalized` and `base.Family`. Read `lexers/clike.py` and `lexers/go.py` for how a lexer
  keeps C1 in step with the lexer by placing blocks or opening a line in STRING.
- Produces: `sql.FAMILY = Family("sql", (".sql",), MARKERS, lex)`. Pick `MARKERS` so that `rules.comment_lines` never
  re-reads a raw line on its own. The lexer places every comment line.

**Rulings (each one gets a test, written first):**

1. **Dialect.** A file is read in MySQL mode if it holds a `/*!` executable comment, a backtick-quoted identifier
   outside strings and comments, or a line that starts with the `DELIMITER` client command (any case). Any other file
   is read in standard mode. Test: `"DELIMITER $$\nCREATE PROCEDURE a() BEGIN SELECT 1; END $$\n"` followed by a
   second procedure ending `END $$` and `DELIMITER ;` lexes without exit 2.
2. **`--` comments.**
   - In standard mode, `--` always starts a comment to the end of the line.
   - In MySQL mode, `--` starts a comment only when it is followed by whitespace or the end of the line, so `1--1` is
     code.
3. **`#` comments.**
   - In MySQL mode, `#` always starts a comment.
   - In standard mode, `#` starts a comment only when it is followed by whitespace or the end of the line. So the
     Postgres operators `#>`, `#>>` and `#-` are code.
   - Pin: Postgres `a # b` (XOR written with spaces) reads as a comment.
4. **`/* */` comments** do not nest.
   - A multi-line block comment is one C1 block.
   - Pin: a nested Postgres or T-SQL comment `/* a /* b */ c */` ends at the first `*/`, so ` c */` reads as code.
   - `/*!...*/` (MySQL executable comments) and `/*+...*/` (optimizer hints) are code, not prose. They are never read
     for C1, C3 or C7, and the lines they span open in STRING.
5. **Strings `'...'`.**
   - `''` is a quote.
   - Strings may span lines.
   - In MySQL mode, and in a Postgres `E'...'`/`e'...'` string, a backslash escapes the next character. Elsewhere a
     backslash is literal: `'C:\'` is complete.
   - Prefixes `N`, `X`, `B` and `U&` are plain letters before the quote.
6. **Quoted identifiers.** `"..."` (with `""`) and MySQL backtick identifiers (with a doubled backtick) are content.
   - T-SQL `[...]` is code.
   - Pin: `[a--b]` reads a comment.
7. **Dollar quoting (standard mode).**
   - `$tag$...$tag$`, where the tag is empty or `[A-Za-z_][A-Za-z0-9_]*`, opens only when the `$` does not follow an
     identifier character (`[A-Za-z0-9_$]`). So `$1` and `a$b$` open nothing.
   - The body up to the identical closing tag is lexed as SQL in standard mode, so plpgsql comments are judged.
   - If the body raises `LexError`, the whole body is content instead, with no exit 2.
   - A dollar quote that never closes raises `LexError` at its opening line.
8. **Unterminated input.** A string, quoted identifier or block comment that never closes raises `LexError` with its
   opening line.
9. **CRLF** behaves as LF.

- [ ] **Step 1: Write the failing tests in `tests/test_sql.py`.** Write one test per ruling, using `support.found`,
  plus at least these:
  - `test_two_dash_lines_are_one_block`: `"-- one\n-- two\nSELECT 1;\n"` gives `[("C1", 1)]`.
  - `test_a_trailing_comment_is_read`: `"SELECT 1; -- see ADR-9\n"` gives `[("C3", 1)]`.
  - `test_a_dash_pair_in_a_string_is_content`: `"SELECT '-- see ADR-9';\n"` gives `[]`.
  - `test_a_multi_line_string_is_content`: `"SELECT 'a\n-- see ADR-9\n';\n-- see ADR-8\n"` gives `[("C3", 4)]`.
  - `test_a_plpgsql_comment_is_judged`:
    `"CREATE FUNCTION f() RETURNS int AS $$\nBEGIN\n  -- see ADR-9\n  RETURN 1;\nEND;\n$$ LANGUAGE plpgsql;\n"` gives
    `[("C3", 3)]`.
